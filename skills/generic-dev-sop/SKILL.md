# 通用项目开发 SOP

把每项功能作为「计划、契约、UI、实现、测试、证据」同步交付的可追踪闭环；把整个项目作为「底座 → 纵向切片 → 阶段门禁」的迭代推进。除纯文案、无行为变化的单行修改外，不得跳过步骤；没有 UI 的后端/基础设施功能可跳过视觉设计稿，但必须在开发记录中说明原因。

## 适用场景与边界

**该用**：从零搭建并完整交付的新项目（前端 / 后端 / 跨端客户端 / 服务端）；需要规范化流程、多角色协作与质量门禁的中大型项目；希望每个功能「计划 → 实现 → 测试 → 证据」可追溯的团队。

**不该用**：纯文案或无行为变化的单行修改；已有仓库的快速小改动；一次性脚本、Demo、原型验证。这些场景直接改代码即可，不必走完整 SOP。

**轻量用法**：小型项目可只走「项目搭建 + 任务计划 + 单功能闭环」，跳过「完整交付」中的灰度、合规、回滚演练等门禁，并在 README 记录跳过原因。

## 快速上手

1. 说「用这个 SOP 从零搭一个 XX 项目」，并指定技术栈（或回车采用 `default-stack.md` 默认组合）。
2. 按 `architecture-template.md` 产出架构决策，按 `task-plan-template.md` 产出任务计划。
3. 每个功能按「第三部分」闭环交付，记录写入 `references/features/<功能短名>.md`。
4. P0 全绿后走「第四部分」发布候选、灰度回滚与交付检查。

状态仅使用：`未开始`、`分析中`、`设计确认`、`开发中`、`审查测试中`、`已完成`、`阻塞`。

## 生命周期总览

新项目按四步推进，功能闭环可循环执行，直到 P0 全部完成再进入交付：

```text
一、项目搭建（架构决策 + 质量底座 + 记录机制）
  → 二、详细任务计划（阶段 / 任务 / 验收 / 门禁）
    → 三、单功能开发闭环 × N（确认计划→需求→方案→记录→设计稿→数据→开发→审查→回写）
      → 四、完整交付（发布候选 → 灰度回滚 → 文档同步 → 项目交付检查）
```

## 第一部分：项目搭建

新项目先搭底座，不直接堆业务页面。

### 1. 确认工程边界

- 新工程放独立目录、独立 package 边界；旧仓库只读，只作为功能与行为基线，禁止复制、import 或 workspace-link 旧实现。
- 固定包管理器与锁文件，全仓统一；开发与 CI 使用同一安装命令。
- 先确认新工程根目录，不要在旧仓库内覆盖创建。

### 2. 确认技术栈

启动开发前先与用户确认技术栈，避免中途返工：

- 按项目形态展示 `references/default-stack.md` 的默认组合作为推荐（Web/桌面、跨端移动、服务端各一套）。
- 用户指定技术栈（如「用 Vue」「用 Go」）→ 记录并以用户为准，写进 `references/architecture.md` 的「固定技术栈」节。
- 用户未指定或直接回车跳过 → 视为同意使用默认，采用 `references/default-stack.md` 的组合，并在架构决策中注明「默认技术栈，用户已确认跳过选型」。
- 确认结果与理由写入架构决策；后续所有实现按该栈执行，不重复争论选型。

### 3. 输出架构决策（按 `references/architecture-template.md` 创建 `references/architecture.md`）

- 产品边界：P0/P1/P2 与「明确不做」清单，冻结首版范围。
- 固定技术栈与理由；优先复用团队已验证的框架、分层与平台桥接模式，不重复发明。
- 技术栈选型：用户指定则以用户为准；未指定时默认采用 `references/default-stack.md` 的已验证组合，不重复争论选型。
- 目录结构与职责边界：技术职责先分层，业务再按模块归档；写入「允许/禁止」对照。
- 数据模型：主库选择、核心表/模型、稳定 ID 与时间约定、迁移与兼容策略。
- 接口契约：API 前缀、统一错误码格式、鉴权/RBAC、实时事件边界。
- 安全与隐私底线：密钥只存环境变量、日志脱敏、最小权限、审计留痕。
- 可行性风险与决策门：每项高风险能力列出 J0 必须验证的门槛。
- 决策结果写入 `references/architecture.md`，作为后续所有实现的依据；有改动同步更新。

通用目录骨架（技术职责分层 + 业务模块归档）：

```text
前端（Web/Electron）:
  src/core/          # model、schema、logic、atom、constants、enums、config
  src/store/         # 状态层，唯一业务状态源
  src/layout/        # 页面与整体布局组合
  src/features/<模块>/{data,state,view}/
  tests/             # 单元与编译期测试，禁止与生产代码共置

跨端客户端（如 Flutter）:
  lib/app/           # 启动、主题、路由、应用壳
  lib/core/          # HTTP、错误、日志、配置、通用组件
  lib/domain/        # 共享领域模型
  lib/features/<模块>/{data,state,view}/
  lib/platform/      # 平台桥接层，只在这里调用系统 API
  test/fixtures/     # 固定轨迹、API、样本

服务端（如 NestJS）:
  src/common/        # filter、guard、错误码、日志、requestId
  src/config/        # 环境配置与启动校验
  src/database/      # data source、migration、seed
  src/modules/<模块>/  # controller + service + schema/DTO
  test/{unit,contract,e2e}/
```

约束：状态层是唯一业务状态源，组件只渲染 Store 输出并转发事件，不持有私有业务状态；平台差异用运行时适配器判断，禁止用构建分叉；外部输入先在 DTO/校验层验证再进业务代码；Controller 保持薄层。

### 4. 输出分阶段任务计划（按 `references/task-plan-template.md` 创建 `references/task-plan.md`）

按「第二部分」的结构编写。计划是开发期间唯一总计划，状态持续回写。

### 5. 搭建质量底座

- 脚手架完成「干净安装 → 启动 → format/lint/type → 定向单测 → build」全链路可跑，并把命令固化到 README。
- 初始化并提交配套文件：`.gitignore`、`.editorconfig`、lint（ESLint/Stylelint 等）+ Prettier、commitlint + husky、`.env.example`（缺关键变量启动失败并说明字段）、CI 工作流。
- 建立 CI 门禁：故意破坏 format/type/test/契约会使 CI 失败。
- 单元测试与编译期测试统一放根目录 `tests/`，禁止与生产代码共置。
- 服务端补充：容器化配置（compose/Dockerfile）、migration 命令、健康检查与优雅关闭。
- 依赖安装缓慢时配置镜像加速（npm/pnpm 用 npmmirror、pip 用清华源），不阻塞流程本身。

### 6. 建立开发记录机制

- 从 `references/development-record-template.md` 复制到 `references/features/<功能短名>.md`。
- 全程更新这份「本次开发记录」；不要只在对话中描述进度。

## 第二部分：详细任务计划（references/task-plan.md）

### 计划文档结构

1. **执行原则**：纵向切片交付；用户流程先行；单一业务真相；每个非平凡切片留最小可运行检查。
2. **交付定义**：写成真实闭环（安装 → 授权 → 首屏 → 核心动作 → 完成 → 恢复），不是「页面都能点」。
3. **范围、估算与关键路径**：阶段估算、团队规模下的日历估计、关键路径文字图。
4. **阶段总览**：`| 阶段 | 目标结果 | 估算 | 前置 |`。
5. **详细任务**：每阶段一组 `#### <阶段>-<序号>：任务名`，含状态、职责要点与验收。
6. **功能矩阵**：`| 域 | P0 | P1 | P2 |`。
7. **质量门禁**：切片级 / 阶段级（命令清单）/ 发布候选级。
8. **团队与责任边界**：建议最小团队角色；高冲突点单一 owner。
9. **第一批执行顺序**：计划批准后严格按序执行，不先扩 UI。

### 任务条目规范

- 任务拆分可独立验证，禁止「实现功能」一类无法验收的笼统条目。
- 每条任务必须有明确 `验收：` 条件（可观察、可判定）。
- 高风险/未验证能力（跨端、后台、权限、平台差异）先进 J0 小样，出口门禁通过后才扩范围。
- 计划中先放里程碑纵向切片，再放同类扩展；新增需求先进入功能矩阵定 P0/P1/P2，不直接插入当前阶段。

## 第三部分：单功能开发闭环

### 1. 确认计划进度

- 定位本功能对应阶段、任务条目、优先级、前置与验收条件。
- 核对现有记录、未完成依赖、脏工作区与本功能重叠的改动。
- 在开发记录写明「开始前状态」与本次允许范围；计划不存在时先补最小计划，不直接编码。

### 2. 理解并分析需求

- 明确用户目标、主流程、输入/输出、异常路径、权限与平台差异。
- 列出可观察验收条件、非目标和需用户确认的决策。
- 追踪相关调用链、现有数据模型、组件与测试；优先复用项目既有模式。

### 3. 设计最小方案

- 给出最小可行方案：模块边界、状态流、错误处理、回滚/取消与性能风险。
- 记录方案选择、替代方案与不做项，等待必要确认后再开发。

### 4. 更新开发记录

- 将方案、任务拆分、完成标准、文件边界、风险与测试计划写入开发记录。
- 同步总计划条目状态；仅在满足验收时标记完成。

### 5. 设计稿（有 UI 时强制）

- 先输出覆盖默认、加载、空、错误、禁用/无权限、弱网/离线状态的静态稿，再开始实现。
- 无 UI 功能在记录「设计稿影响」写明依据。

### 6. 构造数据结构

- 实现前定义领域模型、输入校验、持久化字段、迁移与兼容行为。
- 使用稳定 ID、可序列化数据；禁止把运行时句柄、DOM/平台对象写入持久化模型。
- 涉及命令历史、媒体、导出或 IPC 时补齐逆操作/回滚、错误码与 schema 校验。

### 7. 按方案开发

- 仅实现已确认范围，复用既有组件、工具与依赖；新增依赖在记录说明必要性。
- 编码规范见 `references/coding-standards.md`；技术栈绑定规则以项目级 coding-rules skill 为准。
- 每完成一个可验证切片，更新开发记录状态与证据。
- 用户可见文案走多语言资源，默认语言对齐。

### 8. 审查与测试

- 按 `references/review-checklist.md` 逐项审查后交付。
- 先自审：范围漂移、重复代码、类型/校验、错误处理、数据安全、并发与数据丢失风险。
- 为非平凡逻辑留最小可运行检查；UI 改动做构建/类型与必要视觉检查。
- 日常开发默认「变更测试 + 直接调用链测试 + typecheck + 受影响文件 lint」；全量门禁仅在阶段出口、跨模块重构、构建/配置调整、发布候选前执行。
- 记录执行的命令、结果与已知缺口；失败必须修复或标记阻塞，不能静默略过。

### 9. 回写进度

- 将开发记录更新为最终状态，附变更文件、测试证据、遗留风险与下一步。
- 同步总计划任务状态与功能矩阵。
- 只有代码、测试、设计稿（如适用）与计划记录一致时才交付；否则说明未完成部分。

## 功能交付前检查

- [ ] 计划与开发记录状态一致。
- [ ] 需求、方案、非目标与验收条件已记录。
- [ ] UI 设计稿已同步，或已记录无 UI 影响。
- [ ] 数据结构、迁移与校验已说明。
- [ ] 实现符合方案，多语言资源对齐。
- [ ] 所有声明模块有清晰多行中文注释，路径别名解析一致，无跨层级导入。
- [ ] 审查、测试与必要构建/视觉检查通过或明确说明缺口。
- [ ] 总计划与功能矩阵已回写进度。

## 第四部分：完整交付

P0 全部开发完后，把项目从「能跑」推进到「能交付」。

### 1. 交付定义

- 功能矩阵 P0 全绿，且无「页面有、数据假」「接口有、客户端不可达」「单平台占位」。
- 每个 P0 功能按任务计划的验收条件通过，真机/现场证据已回写。
- 计划、契约、设计稿、实现、测试、文档一致，无遗留阻塞项。

### 2. 发布候选门禁

- 干净环境可重复安装、构建、部署；migration up/down、备份恢复演练通过。
- 真实安装、升级、权限、后台、离线、回滚路径验证通过。
- 鉴权、日志、存储、依赖漏洞与 secret 扫描安全审查通过；高风险清零，其余有 owner 与期限。
- 合规：数据来源授权、隐私政策、未成年人保护、商店/发布要求签字。
- 性能、功耗、稳定性达到任务计划冻结的阈值。

### 3. 灰度与回滚

- 小规模灰度收集真实指标（崩溃率、错误率、核心功能漏斗），达到门槛再扩大。
- 配置、内容、数据迁移、客户端各有独立回滚，回滚不破坏用户数据。
- 停止灰度不损坏既有用户状态；回滚演练实际执行过。

### 4. 文档同步

- README 与实际命令一致；API 文档/Swagger 与契约一致。
- CHANGELOG/发布说明记录变更与升级影响；操作/运维手册覆盖部署与回滚。
- 删除已失效的临时文档与占位说明。

### 5. 项目交付检查

- [ ] P0 功能矩阵全绿，无假数据、不可达、占位项。
- [ ] 发布候选门禁逐项通过，或有明确 owner 与期限的例外。
- [ ] 灰度与回滚演练完成，无数据丢失风险。
- [ ] 文档、API、CHANGELOG 与实际实现一致。
- [ ] 开发记录与总计划已回写最终状态，遗留风险有后续项。
- [ ] 可交付产物（安装包/构建/部署配置/发布说明）已产出并验证。

读取 `references/architecture-template.md` 创建架构决策，未指定技术栈时按 `references/default-stack.md` 取默认组合，读取 `references/task-plan-template.md` 创建或更新总计划，读取 `references/development-record-template.md` 创建或更新本次开发记录，编码与审查分别按 `references/coding-standards.md`、`references/review-checklist.md` 执行。
